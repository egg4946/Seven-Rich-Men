レビュー日: 2026-09-14（Asia/Tokyo）

対象: 初回コミット `80a3722` を基準に、現在の作業ツリーに追加されたサーバー・通信プロトコル・オンラインクライアントと、既存コードの関連変更。

## 1. 同じ受付に対する同時回答が stale として破棄される

- 主な箇所: `apps/server/src/room.ts:249`
- 関連箇所: `apps/web/src/game/store.ts:400`

### 再現手順

1. Aが8を置き、BとCの両方に4止めの受付を開く。手番順はA→B→Cとする。
2. BとCが同じ `version` の画面から4止めを宣言する。
3. サーバーにCの回答が先に到着すると、その回答の適用でゲーム全体の `version` が増える。
4. Bの回答は、同じ受付が継続していてB自身も未回答なのに、`stale` で拒否される。

期待: 両方の回答を受理し、宣言の優先順位は通信の到着順ではなく手番順で判定する。

実際: Bの回答は `{ ok: false, code: 'stale' }`。クライアントは `stale` のエラー通知を抑制するため、失敗したことも伝わらない。再操作しなければ時間切れでスキップ扱いになり、Cの宣言が有効になる。7渡し・ジョーカーへの割り込み回答でも同じ競合が起こる。

### 修正の方向

受付を識別するIDと、プレイヤーごとの回答済み状態で重複・期限切れを検証する。他人の回答だけで進んだ更新番号を理由に、同じ受付への有効な回答を拒否しない。通常手番の古い操作を拒否する検証は維持する。拒否された操作を画面が黙って捨てないことも必要。

### 確認方法

`Room` に3人の対戦状態を用意し、C→Bの順で同一versionの `REACT` を送信するテストで再現。Bの期待結果 `ok: true` に対し、実際は `ok: false / stale`。

## 2. 対戦を識別するIDがなく、再戦後の状態を古いものとして捨てる

- 主な箇所: `apps/web/src/game/store.ts:245–247`
- 関連箇所: 同ファイル `228–238`、`packages/protocol/src/index.ts` の `RoomView` / `GameUpdate`

### 再現条件・手順

1. クライアントが前の対戦の `phase: playing, version: 80` を表示している。
2. 通信途絶中に終局と再戦があり、その2つの通知を受信できない。
3. サーバーの切断検知前に再戦が始まり、当該プレイヤーの席が新しい対戦にも含まれているケースで再接続する。
4. 最新の `RoomView` は再び `phase: playing` で、新しいゲームの `version` は0などの小さい値になる。

期待: 新しい対戦の手札と盤面へ切り替わる。

実際: 保存済みの部屋も `playing` のため `startedNewGame` がfalseになり、古いviewを消さない。さらに新しい `version` が前の対戦より小さいため `onGame` が破棄し、古い手札・盤面が残る。新しい対戦のversionが追いつくか、ページをリロードするまで正常に同期できない。

サーバーが切断済みと認識してから再戦を始めた場合は、`Room.start()` がそのメンバーを除外するため、この問題とは別の経路になる。今回の指摘は、通知が欠落しても席が保持された場合の対戦識別の問題。

### 修正の方向

サーバーが対戦ごとに一意な `matchId` を作成し、部屋情報・ゲーム更新・操作要求に含める。versionは同じmatchId内でのみ比較し、matchIdが変わればview・選択・ログ・タイマーを初期化する。前の対戦から遅れて届いた操作もmatchIdで拒否できる。

### 確認方法

オンライン接続をモックし、実際のZustandストアの受信ハンドラーへ「旧対戦version80→再接続→playingの部屋情報→新対戦version0」の順に通知するテストで再現。新しい手札 `['S6', 'C1']` を期待したが、古い `['S1']` が残った。実ブラウザで通信を遮断して再戦をまたぐ経路は未確認。

## 3. 短時間の切断・再接続で、同じ手番の基本時間が回復する

- 主な箇所: `apps/server/src/room.ts:285–291`
- 関連箇所: `disconnect()`、`join()`、`openTimer()`、`closeTimer()`

### 再現手順

1. 基本時間1000ms・持ち時間2000msで人間の手番を開始する。
2. 900ms待って切断する。
3. CPUが代打の操作を行う前に、同じトークンで再接続する。

期待: 同じ操作待ちの時間経過を引き継ぎ、基本時間を使い直せない。

実際: 切断で `closeTimer()` がタイマーを削除する。基本時間内のため持ち時間の減少は0。再接続すると `openTimer()` が現在時刻から新しいタイマーを作り、経過時間が900msから0msへ戻る。

この操作を繰り返すと、持ち時間を減らさず同じ手番の判断時間を延ばせる。既定設定では基本時間10秒が再付与される。

### 修正の方向

CPUへの操作委譲と、同じdecisionKeyの時間経過の記録を分離する。同じ受付に戻った場合は以前の開始時刻・期限を引き継ぎ、CPUが別の場面へ進めた場合にだけ新しい基本時間を付与する。

### 確認方法

偽時計で900ms進め、`disconnect()` と同じトークンの `join()` を連続実行。再送された `TimerView.elapsedMs` の期待値900に対し、実際は0だった。

## 4. 同じソケットが複数メンバーに登録され、切断後も部屋が残り続ける

- 主な箇所: `apps/server/src/room.ts:129–146`
- 関連箇所: `apps/server/src/rooms.ts:30–45`、`Room.memberBySocket()` / `disconnect()`

### 再現手順

1. 1本のソケットから、トークンAでロビーへ入室する。
2. 同じソケットから、同じ部屋へ別の有効なトークンBで再度 `room:join` を送る。
3. ソケットを切断し、ロビーの猶予時間・空室TTLの両方を超えるまで待つ。

期待: 同じソケットの別メンバー登録を拒否するか、登録を安全に置換する。切断後は接続数が0となり、部屋が片付く。

実際: `Room.join()` はトークンだけで既存メンバーを探すため、新しいメンバーにも同じsocketIdを登録する。`RoomManager` も同じ部屋への再入室では既存の紐付けを解除しない。切断時は `memberBySocket()` が最初の1人しか返さず、後のメンバーのsocketsに死んだsocketIdが残る。`connectedCount > 0` のままなので空室TTLが働かず、部屋が残り続ける。

通常UIの操作だけでは起こしにくいが、サーバーが受理する正しい形式の要求だけで再現できる。複数の部屋で繰り返すと、実際には誰もいない部屋を残せる。

### 修正の方向

socketIdに対してメンバーを一意に紐付け、既に登録済みのソケットが別トークンで入室しようとしたら拒否するか、以前の登録を完全に解除する。同一トークンを複数ソケットで使う再接続・複数タブ対応とは分けて扱う。

### 確認方法

`RoomManager.join()` を同じsocketId・別トークンで2回実行し、`disconnect()` 後に10000ms進めた。空室TTL1000ms・ロビー猶予5000msに対し、期待 `roomCount: 0`、実際 `roomCount: 1`。
